# Data model (schema v2)

Source of truth: `prisma/schema.prisma`. Migration: `prisma/migrations/20261113_schema_v2/migration.sql`
(additive on top of `20261015_initial`). Requirements: `docs/requirements/requisitos_plataforma_ricaurte_tours_v2.0.md`
§7, §10.4, §11, §12.5, §15–17.

## Conventions

- PostgreSQL, Prisma 7 (`prisma-client` generator to `src/generated/prisma`, `@prisma/adapter-pg`).
- UUID primary keys generated by Prisma; `snake_case` tables/columns via `@map`/`@@map`; `created_at`/`updated_at`.
- Catalog and accounts use soft delete (`deleted_at`). Public entities have a unique `slug`.
- **Money is integer COP cents in `BIGINT`** (`*_cents`), matching Wompi `amount_in_cents`. Never `Float`.
  Convert to `number` only after `Number.isSafeInteger` (domain `assertCents`). Currency columns are `COP`
  (DB CHECK on payments, ledger, abonos, refunds, reservations). Legacy v1 `Decimal` columns stay readable.
- Rates and percentages: `Decimal(14,4)` for the informative exchange rate, basis points (`Int`) for promotions.
- Price data carries `is_fictitious` (default `true` on catalog prices, rules, seasons, age rules, promotions)
  until the agency matrix is loaded (PC-4). Quotes/reservations copy the flag from the pricing output.
- Hashes are SHA-256 hex in `CHAR(64)` (session tokens, one-time tokens, IP/UA, webhook payloads).
- Lines marked `/// PII` in the schema hold personal data: collect only with a defined purpose, never log.

## Key rules for application code

- **Ownership (IDOR):** `customer_id` is indexed on quotes, reservations, payments, ledger entries, abonos,
  savings plans and PQR. Resolve the session user's `Customer` (`customers.user_id`) and always filter by it;
  staff access goes through RBAC permissions, never through a client-supplied id alone.
- **Reservation status** changes only through `transitionReservation`; persist the new status with
  `UPDATE ... WHERE id = $1 AND version = $2` (bump `version`) and insert the returned history row in the
  same transaction. `actor_id` is null for `SYSTEM` and guest customers; `from_status` is null only on creation.
- **Cupos:** reserve with a conditional update (`held_seats + confirmed_seats + n <= capacity` in the `WHERE`);
  the v1 CHECK `departures_capacity_check` is the backstop. Prisma field `soldSeats` maps to `confirmed_seats`.
- **Webhooks:** insert `PaymentWebhookEvent` first; `(provider, provider_event_id)` is unique, so a replay fails
  the insert and has no effect. Wompi events have no event id: derive it deterministically (e.g. SHA-256 of
  transaction id + status + `timestamp`). Store `checksum_valid`, `payload_sha256` and a minimised payload.
  Mark the payment approved only after server-side transaction lookup (`payments.verified_at`).
- **Ledger:** balance = `SUM(amount_cents)` per reservation or savings plan. Positive = money in; negative =
  void/refund. Unique `(payment_id, kind)`, `(manual_abono_id, kind)`, `(refund_id, kind)` prevent double
  credit. A manual abono is credited once as `MANUAL_ABONO` (never also as `PAYMENT_APPROVED` for its
  `MANUAL` payment). Corrections are `ADJUSTMENT` rows, never updates.
- **One-time tokens:** consume with `UPDATE one_time_tokens SET used_at = now() WHERE token_hash = $1 AND
used_at IS NULL AND expires_at > now()` and check one row was affected.
- **Sessions:** cookie holds the random token; only its hash is stored. Revoke by setting `revoked_at`.
- **MFA:** TOTP secrets are encrypted by the application (key from env), `last_used_step` blocks replay.
- **Emails** are lowercased before every write (`users_email_lowercase` CHECK); look up with lowercased input.
- **Consent:** each grant or withdrawal is a new `ConsentRecord` row referencing an `APPROVED` `LegalDocument`.
- **Agency settings:** one row (`id = 1`); every value is nullable and must come from the agency (RNT, NIT,
  contacts, social). Render nothing rather than a placeholder.
- **Quote lines** are snapshots: `component_id`/`price_rule_id` are deliberately not foreign keys.

## Database-level rules (hand-written SQL, not modelled by Prisma)

Prisma does not represent CHECK constraints, triggers or functions, so `migrate diff` neither recreates nor
drops them. Keep them in mind when writing tests or seeds.

| Rule                                                                                   | Object                                                                                                                                                                                                                        |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lowercase email for new/updated rows (`NOT VALID`: v1 rows not scanned)                | `users_email_lowercase`                                                                                                                                                                                                       |
| Positive amounts, `COP` only                                                           | `payment_transactions_amount_valid`, `manual_abonos_amount_valid`, `refunds_amount_valid`, `reservations_amounts_valid`, `savings_plan_installments_amount_positive`, `*_price_cents_check`, `savings_plans_goal_cents_check` |
| Ledger sign matches kind; source FK matches kind; reservation or savings plan required | `ledger_entries_amount_valid`, `ledger_entries_source_valid`                                                                                                                                                                  |
| Price rule targets exactly one product; promotion discount shape and dates             | `price_rules_target_valid`, `promotions_discount_valid`, `seasons_range_valid`                                                                                                                                                |
| Exactly one target in polymorphic links                                                | `package_components_one_target`, `media_attachments_one_owner`                                                                                                                                                                |
| Singleton settings row                                                                 | `agency_settings_singleton`                                                                                                                                                                                                   |
| Append-only (UPDATE/DELETE raise `restrict_violation`)                                 | triggers on `ledger_entries`, `reservation_status_history`, `consent_records` via `rt_reject_mutation()`                                                                                                                      |

Because of the append-only triggers, test cleanup must use `TRUNCATE` (not `DELETE`) or a fresh database,
and foreign keys into those tables use `ON DELETE RESTRICT` (users and customers are soft-deleted).

## Legacy (v1) models kept for compatibility

Nothing was dropped. These models stay readable; new code must not write them.

| Legacy model (table)                                                                              | Superseded by                                                              |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `User.role` (`UserRole` enum)                                                                     | RBAC: `UserRoleAssignment` + `Role`                                        |
| `Booking` (`bookings`), `BookingTraveler`                                                         | `Reservation`, `Traveler`                                                  |
| `BookingStatus` enum                                                                              | `ReservationStatus`                                                        |
| `LegacyPayment` (`payments`), `LegacyPaymentEvent` (`payment_events`)                             | `Payment` (`payment_transactions`), `PaymentWebhookEvent`                  |
| `LegacyPaymentStatus` (DB type `PaymentStatus`)                                                   | `PaymentStatus` (DB type `PaymentStatusV2`)                                |
| `PaymentPlan`, `Installment`                                                                      | `SavingsPlan` + `SavingsPlanInstallment` + `LedgerEntry`                   |
| `SavingsMovement`, `SavingsPlan.goalAmount`, `Departure.price`, `TourPackage.basePrice` (Decimal) | `LedgerEntry`, `goalCents`, `priceCents`, `basePriceCents`                 |
| `Agreement`, `AgreementAcceptance`                                                                | `LegalDocument`, `ConsentRecord`                                           |
| `SiteSetting` (key/value)                                                                         | `AgencySetting` for typed agency data (`SiteSetting` may still hold flags) |
| `PqrsTicket.bookingId`                                                                            | `PqrsTicket.reservationId`                                                 |

Prisma-only renames (no DB change): models `Payment`→`LegacyPayment`, `PaymentEvent`→`LegacyPaymentEvent`,
enum `PaymentStatus`→`LegacyPaymentStatus` (`@@map`), field `Departure.confirmedSeats`→`soldSeats` (`@map`).
No enum value was renamed or added to an existing enum. A later migration may drop legacy tables once data is
migrated and the agency confirms; that is out of scope here.

## Migration notes

- Generated with `prisma migrate diff --from-schema <v1 schema copy> --to-schema prisma/schema.prisma --script`,
  plus the hand-written section at the end of the file.
- Only `ALTER COLUMN` statements are `DROP NOT NULL` (`departures.price`, `savings_plans.goal_amount`,
  `pqrs_tickets.customer_id`). New `NOT NULL` columns on existing tables all have defaults.
- Verified locally with `prisma dev` (Prisma Postgres): `migrate deploy` from scratch succeeded, `migrate diff`
  database→schema reported no difference, and the v2 SQL applied cleanly over a schema seeded with v1 rows.

## Open questions (agency / later tasks)

- Categories: §4.1 asks for panel-configurable categories; v2 uses the fixed `DestinationCategory` enum
  requested for this phase. A `Category` table can replace it later.
- Destination `category` is nullable for v1 rows; backfill when the catalog arrives.
- Whether travelers' names/documents are required (§10.3) and whether age is evaluated at booking or travel date (§6.3).
- PQR response times (SLA policy) to compute `first_response_due_at` / `resolution_due_at`.
- Four-eyes rule for manual abonos (approver different from registrar) is not enforced in the DB.
- Quote validity period, rounding policy and how `pricingVersion` strings are issued (PricingService task).
- Role/permission seed data (permission keys per role, §12.5 "Operador" maps to `ADVISOR`).
- Data retention periods for sessions, tokens, webhook payloads and PII (Ley 1581).
